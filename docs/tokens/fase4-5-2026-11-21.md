## Fase 4.1: Ponytail (NÃO instalado nem testado)
- **Lido:** repositório `DietrichGebert/ponytail`, tag `v5.3.3` (commit `7801d06`), licença MIT. `plugin.json`, hooks (`hooks/claude-codex-hooks.json`) e a lista de comandos; busca por chamadas de rede e execução de processos nos `.js`.
- **O que faz:** modo "dev sênior preguiçoso" (resposta mais simples possível). Hooks `node` em `SessionStart`, `SubagentStart` e `UserPromptSubmit` (a cada sessão, retomada, `/clear`, compactação, subagente e prompt); grava um CSV em `~/.config/ponytail/` (fora do projeto, ligado por padrão); webhook só se `webhookUrl` for preenchido (código de envio em `hooks/band/register.tsx`); roda `git ls-files` para mapear o repositório.
- **Por que parou:** o teste seria carregar o plugin (hooks rodando código de terceiros) numa sessão do Claude; o classificador do modo auto bloqueou a execução (`--plugin-dir`), por se tratar de código de terceiros que não foi lido por inteiro (hooks `.js` lidos só por busca de padrões). A ordem exige ler antes de instalar; **não contornei o bloqueio**.
- **Avaliação de custo/benefício (sem medição):** o plugin injeta instruções a cada sessão (`ponytail-instructions.js` tem ~5,6 KB) e muda o estilo de resposta de código; a tarefa de referência (rodar testes e resumir) quase não produz código, então dificilmente atingiria 5%. Pode também conflitar com nosso fluxo de spec/TDD/documentação, e roda em todos os papéis do Maestri. **Recomendação: não instalar**, a menos que o Diego queira um experimento supervisionado.
- **Se for testar depois:** `claude plugin marketplace add DietrichGebert/ponytail` + `claude plugin install ponytail@ponytail --scope local`, fixar a tag `v5.3.3`, desligar `ledger` e `sendNames`; rollback: `claude plugin uninstall ponytail@ponytail`, `claude plugin marketplace remove ponytail` e apagar `~/.config/ponytail/`.

## Fase 5: medição
**Método:** `claude -p "<tarefa>" --model sonnet --output-format json --allowedTools "Bash(pnpm:*)"` em sessão nova (sem `--continue`), 3 execuções, média do campo `usage` (cache criado + cache lido + entrada; saída; custo). Tarefa: "Rodar `pnpm --filter @leguele/shared test` e resumir as falhas" (45 arquivos, 294 testes, todos passando).

- Contexto inicial (1º turno, cache criado numa sessão nova): ~48 mil tokens (system + ferramentas + CLAUDE.md + skills + memória). É a medida mais próxima do `/context` que o modo `-p` oferece.
- rtk: ~7,3 mil tokens economizados em 195 comandos (23,6%), em `rtk gain` na Fase 1.

**Limites desta medição:** (a) não há linha de base "antes" comparável: a Fase 0 só estimou o contexto por caracteres (÷ 4) porque o `/context` é interativo; as mudanças da Fase 1 e 2 já estavam aplicadas quando o benchmark rodou; (b) 3 execuções variam muito (cache criado de 3 mil a 20 mil, por cache frio); (c) as reduções de `MAX_MCP_OUTPUT_TOKENS`/`BASH_MAX_OUTPUT_LENGTH` só aparecem em saídas grandes, que esta tarefa não produz. Portanto **não é possível afirmar um percentual de economia**, só registrar o valor atual para comparar com futuras mudanças. Para um "antes" real, rode o mesmo comando com `CLAUDE_CONFIG_DIR` apontando para uma cópia do settings original (`~/.claude/backups/tokens-2026-11-21/`).
